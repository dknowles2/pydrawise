# AGENTS.md

This file provides guidance to AI coding agents (Claude Code, Codex, Cursor, etc.) when working
with code in this repository.

## What this is

Pydrawise is an async Python 3 library for the Hydrawise sprinkler controller API. No official
relationship with Hydrawise/Hunter. Requires Python >= 3.11.

## Commands

Dependencies are managed with `uv`, but `pytest`/`ruff`/`mypy` aren't declared as project
dependencies — they only come from `requirements-test.txt`/`requirements-dev.txt`, which must be
installed into the venv explicitly before `uv run` will find them:

```sh
uv pip install -r requirements-test.txt -r requirements-dev.txt
```

Then:

```sh
uv run pytest                              # full test suite
uv run pytest tests/test_hybrid.py         # one file
uv run pytest tests/test_hybrid.py::test_get_user   # one test
uv run pytest -k throttl                   # by name substring

uv run ruff check .                        # lint (matches CI)
uv run ruff format .                       # format

uv run mypy .                              # typecheck (matches CI; covers pydrawise/ and tests/)
```

Docs (mkdocs + mkdocstrings, autogenerated from docstrings — see "Documentation" below):

```sh
uv pip install -e . -r docs/requirements.txt
uv run mkdocs build --strict               # fails on any warning, including broken cross-refs
uv run mkdocs serve                        # local preview
```

`pydrawise/_version.py` is generated by `setuptools_scm` at build/install time and is gitignored —
don't hand-edit it or worry about it being absent in a fresh checkout.

## Architecture

### Four client implementations, one interface

Everything funnels through the abstract `HydrawiseBase` interface (`pydrawise/base.py`), which all
four concrete clients implement identically:

- `client.Hydrawise` — GraphQL API. The default, full-featured client.
- `hybrid.HybridClient` — prefers GraphQL, falls back to (and caches results from) the REST API
  once a `Throttler` token budget is exhausted. Built for pollers (e.g. Home Assistant) that need
  to stay under Hydrawise's GraphQL rate limits without losing responsiveness.
- `rest.RestClient` — REST v1 only. Several `HydrawiseBase` methods aren't representable in the v1
  API and always `raise NotImplementedError` (`get_controller`, `get_zone`,
  `delete_zone_suspension`, `get_sensors`, `get_water_flow_summary`, `get_watering_report`,
  `get_water_use_summary`).
- `legacy.LegacyHydrawise` — synchronous, kept compatible with
  [hydrawiser](https://github.com/ptcryan/hydrawiser). Exposes raw REST JSON via dict-backed
  properties rather than the `schema` dataclasses.

Each has a matching `BaseAuth` implementation in `auth.py` (`Auth`, `RestAuth`, `HybridAuth`) that
owns credential handling and low-level transport for that client. When adding a method to
`HydrawiseBase`, it needs an implementation (or explicit `NotImplementedError`) in all four clients
to stay consistent — grep for an existing method like `get_sensors` across `client.py`, `hybrid.py`,
`rest.py`, and `base.py` to see the pattern before adding a new one.

### Schema models do double duty

`schema.py`'s dataclasses (`Zone`, `Controller`, `Sensor`, etc.) are not plain GraphQL response
types — they're also used to parse REST v1 JSON directly, via `Zone.from_json`/`update_with_json`
and `Controller.from_json`/`update_with_json`. This is what lets `HybridClient` merge a REST poll
into an object that was originally populated by GraphQL. `Zone.update_with_json` takes a
`trust_suspension_sentinel` flag for exactly this reason: the REST API sends the same ambiguous
sentinel value for "truly suspended" and "merely held off by a rain sensor," so callers with a more
reliable GraphQL-derived state pass `False` to avoid flip-flopping a zone's suspension status on
every poll (see the comment in `Zone.update_with_json` for the full story).

`DSL_SCHEMA` (used to build GraphQL queries) is constructed at import time by parsing the raw SDL
in `hydrawise.graphql` — that file is the source of truth for what fields/types exist on the wire;
`schema.py`'s dataclasses are a hand-maintained subset of it.

### GraphQL selection sets are generated, not hand-written

`schema_utils.get_selectors()` walks a dataclass's fields (via `dataclasses.fields` +
`get_type_hints`) and builds the corresponding GraphQL DSL selection set automatically, recursing
into nested dataclasses and expanding `Union` fields into inline fragments. Callers pass a
`skip_fields` list to prune expensive subtrees — dotted paths like `"zones.past_runs"` skip a
field only within a specific descendant (see `parse_skip`). This is why client methods rarely
construct GraphQL selections by hand; adding a field to a `schema.py` dataclass is usually enough
for it to start showing up in queries, as long as it isn't skipped.

### Mutations vs queries

`client.Hydrawise._mutation()` centralizes mutation result handling: a `status == "ERROR"` raises
`MutationError`, `"WARNING"` logs and returns normally, and a falsy non-dict response is treated as
a failed boolean mutation. New mutation-backed methods should go through `_mutation()` rather than
reimplementing this.

## Documentation

- `docs/index.md` is a symlink to `README.md` — edit `README.md`, not the symlink target.
- `docs/reference/*.md` are thin mkdocstrings stubs (`::: pydrawise.<module>` + a `filters` list)
  that render docstrings from the corresponding module. If you add a new public class/module, it
  needs a corresponding stub or it won't appear in the generated docs — `mkdocs build --strict`
  won't catch a missing page, only broken links, so check the rendered nav.
- `docs/usage.md` has hand-written usage examples; keep its code snippets in sync with real method
  signatures (there's no doctest runner enforcing this).
- Cross-references in docs use `[Text][fully.qualified.path]` (mkdocs-autorefs); `mkdocs build
  --strict` will fail if the target isn't rendered anywhere, which is the main way a typo here gets
  caught.

## Testing conventions

- HTTP mocking uses a small custom `MockServer` in `tests/conftest.py` (a real aiohttp
  `TestServer` with a catch-all route you register canned responses against) — not
  `aioresponses`/`responses`. Follow that pattern for new tests that hit `Auth`/`RestAuth`/
  `HybridAuth`.
- The test process timezone is pinned to UTC in `tests/conftest.py` (`os.environ["TZ"] = "UTC"`)
  because several tests assert on UTC offsets and epoch timestamps derived from naive datetimes —
  don't remove that without checking those assertions still hold on a non-UTC machine.
- `pytest-asyncio` runs in `auto` mode (`pytest.ini`), so `async def test_*` functions don't need
  an explicit `@pytest.mark.asyncio` marker.
